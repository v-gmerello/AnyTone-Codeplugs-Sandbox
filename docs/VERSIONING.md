# Versioning

## Policy

The project follows Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

- `MAJOR` changes incompatible public APIs, stored formats, or supported
  workflow contracts after `1.0.0`.
- `MINOR` adds backward-compatible functionality or verified radio profiles.
- `PATCH` fixes backward-compatible defects, validation, or documentation.

## Initial Development

Versions remain `0.x.x` while API contracts, RDT profiles, and validation
procedures are experimental. During `0.x`, a minor increment may contain
breaking changes, which must be documented prominently.

The scaffold uses internal version `0.1.0-SNAPSHOT` for the backend and `0.1.0`
for the frontend. This does not represent a published release.

## Radio Profile Compatibility

Application version and radio-format support are separate concerns. Every
supported profile must identify exact model and discovered format/version
markers plus validated CPS, firmware, and region metadata where relevant.

A new profile can justify a minor release. Correcting generated bytes for an
existing profile is a patch only when it preserves the documented contract; a
required migration or incompatible output policy may require a minor increment
during `0.x`.

## Release Requirements

Before a release:

- all CI gates pass from the tagged revision;
- changelog entries move from Unreleased to the version and date;
- current state and compatibility docs match implementation;
- no secrets, real codeplugs, or generated build artifacts are tracked;
- license and security contact requirements are satisfied;
- supported profile evidence and CPS/radio validation are complete;
- the tag uses `vMAJOR.MINOR.PATCH`.

Do not create releases merely because scaffolding or local experiments exist.
